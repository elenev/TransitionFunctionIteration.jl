## Phase 1 (completed in prior session, confirmed passing)

Full simseries layout transpose: `N_runs × N_periods` → `N_periods × N_runs`.

Motivation: `eachrow` on a 2D StructArray returns strided `SubArray` rows; composing a
range index on top via `view(row, 2:n)` triggers `reindex`, allocating a new index object per
call. Transposing to `N_periods × N_runs` and iterating via `eachcol` gives plain 1D
StructArrays with contiguous Vector columns — `view` is then a simple boolean-masked SubArray
with no reindexing.

## Phase 2 (completed this session)

### Linearize tests uncommented and fixed

Uncommented all tests in `test/test_linearize.jl` and the
`"NGM — perturbation vs simulation linearization"` testset in `test/test_ngm.jl`.

Root cause of failures: `_regress` passes `valnames` (a `Tuple{Symbol}`) and `components(states)`
(a data-bearing NamedTuple) to `MomentArray(data, rows, cols)`. The fallback constructor calls
`Val(col_names)` but receives a full NamedTuple with Vector data, not just keys — `Val` cannot
accept runtime values as type parameters → `TypeError`.

Fix: added `Tuple{Vararg{Symbol}}` to `_HasVarnames` in `src/statistics_types.jl`:
```julia
const _HasVarnames = Union{StructArray, NamedTuple, StatisticsSet, Tuple{Vararg{Symbol}}}
_varnames(names::Tuple{Vararg{Symbol}}) = names
```
This routes plain symbol tuples through the `_HasVarnames` dispatch path (which directly
constructs `MomentArray{rows, cols}`) rather than the fallback `Val(...)` path.

The user also added a `@MomentArray` macro to `statistics_types.jl` (for compile-time-known
names in test helpers) and added `Val{N}` to `_HasVarnames`.

### STPFIMethod test un-broken

`"NGM — STPFIMethod solves to same result"` was marked `@test_broken` because it previously
errored in ForwardDiff at a grid boundary. It now passes consistently when `test_ngm.jl` is
run in isolation. Changed from `@test_broken` to `@test`.

However, the test still fails intermittently when the full test suite is run (but not alone).
Identified as an order-dependent threading issue:

- `STPFIMethod` calls `forecast_next` → `Vfct(point)` inside the nonlinear solver at every
  solver iterate (ForwardDiff perturbs K′, which can exceed the grid → `Throw()` extrapolation)
- When run after other test files, Polyester's thread scheduler distributes work in a different
  order, changing which Tfct coefficients are in-place when each point is solved and therefore
  how close initial guesses are to the grid boundary
- The `TFIMethod` avoids this by computing expectations once with `init_trans` before solving

The issue is left open; options discussed: revert to `@test_broken`, add boundary penalty in
`STPFISystem`, or add `use_threads=false` diagnostic to the test.
